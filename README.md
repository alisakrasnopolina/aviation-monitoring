# Мониторинг авиарейсов

Курсовой проект по дисциплине «Проектирование систем управления данными». Настольное приложение позволяет регистрировать выполнения рейсов, фиксировать вылет и прилёт, учитывать причины задержек и просматривать статистику. Данные и серверная логика реализованы в PostgreSQL, интерфейс — на Python с Tkinter.

| Роль | Операции в приложении |
| --- | --- |
| Оператор | Регистрация выполнения, корректировка плановых времён, смена состояния и указание причины задержки |
| Аналитик | Поиск и фильтрация выполнений, статистика за выбранный период |
| Администратор | Просмотр истории состояний, ведение справочников и пользователей |

PostgreSQL проверяет полномочия, порядок времён и допустимость переходов. История сохраняет начальное состояние, последующие переходы и автора операции, определяемого по учётной записи подключения.

## Развёртывание базы

Понадобятся PostgreSQL 17, DBeaver и Python 3.11 или новее с Tkinter. У PostgreSQL должен работать локальный сервер.

1. В DBeaver подключитесь к служебной базе `postgres` под локальным пользователем `postgres`. Включите автоматическую фиксацию транзакций и отдельно выполните:

   ```sql
   CREATE DATABASE aviation_monitoring_final;
   ```

2. Создайте подключение к `aviation_monitoring_final` под `postgres`. Открывайте файлы из `sql/` в этом подключении и выполняйте каждый целиком командой **Выполнить SQL-скрипт** в указанном порядке.

   ```text
   01_create_tables.sql
   02_insert_data.sql
   04_functions.sql
   05_procedures.sql
   06_triggers.sql
   08_roles.sql
   ```

   Исходные данные содержат записи с уже завершёнными и отменёнными выполнениями. Поэтому их нужно загрузить до установки триггеров. Сразу после загрузки в `public.flight_instance` ожидается **82 записи**. Скрипт `03_queries.sql` предназначен для демонстрации запросов и запускается отдельно.

3. Для первого входа задайте пароли учебным учётным записям. Откройте psql под `postgres` и выполните команды по очереди. psql предложит ввести каждый пароль интерактивно.

   ```text
   \password test_operator
   \password test_analyst
   \password test_admin
   ```

   Если эти учётные записи уже используются в том же экземпляре PostgreSQL, подойдут их действующие пароли. В приложении `test_operator`, `test_analyst` и `test_admin` сопоставлены с `operator1`, `analyst1` и `admin1` через `app_user.db_login`.

## Запуск приложения

Откройте терминал в корне проекта, где находится этот README.

**Windows PowerShell**

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app\main.py
```

**Linux и macOS**

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python app/main.py
```

В форме входа укажите сервер `127.0.0.1`, порт `5432`, базу `aviation_monitoring_final` и учётную запись выбранной роли с её паролем. В поле базы по умолчанию стоит `aviation_monitoring_pr10`, поэтому при чистом развёртывании имя нужно заменить вручную.

## Контрольные проверки

| Проверка | Как выполнить | Контрольный результат |
| --- | --- | --- |
| Серверная логика | Под `postgres` выполнить `sql/07_server_logic_tests.sql` целиком в базе проекта | `PASS: TC-01–TC-18` |
| Матрица доступа | Под `postgres` выполнить `sql/09_access_tests.sql` | `PASS: матрица прав и сигнатура процедуры` |
| Три подключения | Запустить `tests/check_access.py` с указанием базы и ввести пароли по запросу | Отдельная строка `PASS` для каждой учебной роли |
| Интерфейс | Повторить сценарии из `tests/PR11_GUI.xlsx` | Регистрация и просмотр истории доступны назначенным ролям, недопустимое время отклоняется |
| Пороги задержки | Выполнить `sql/10_delay_threshold_analysis.sql` | Для исходной выборки из 70 выполненных рейсов получаются 35, 25, 12 и 5 задержек при четырёх порогах |

Для проверки подключений в PowerShell:

```powershell
$env:PGDATABASE = "aviation_monitoring_final"
.\.venv\Scripts\python.exe tests\check_access.py
```

Для Linux и macOS:

```bash
PGDATABASE=aviation_monitoring_final .venv/bin/python tests/check_access.py
```

Скрипт `07_server_logic_tests.sql` временно переключает учётную запись и откатывает тестовые изменения. Для него нужен локальный `postgres`. Результаты проверок ПР11 и журнал дефекта D-01 сохранены в [tests/test_cases.xlsx](tests/test_cases.xlsx). Они относятся к учебной базе `aviation_monitoring_pr10`. Таблица выше задаёт результаты, которые следует получить при повторении проверок на новой базе.

## Сценарий демонстрации

1. Войдите как `test_operator`. Зарегистрируйте выполнение рейса B61053 с планом 10:00–12:00. На другой свободной дате можно повторить проверку без конфликта с уже созданным выполнением.
2. Попробуйте сохранить плановый прилёт в момент вылета. После отказа укажите допустимое время. Зафиксируйте фактический вылет, причину задержки и фактический прилёт.
3. Войдите как `test_admin`. Откройте историю выполнения и проверьте начальное состояние и последующие переходы.
4. Войдите как `test_analyst`. Укажите период с 1 января 2025 года до 1 февраля 2025 года. Правая граница периода исключается. В исходной выборке отображаются 80 выполнений, из них 70 завершены и 35 выполнены с задержкой вылета.
